## 2. 항목별 검증 결과

### 가격 갱신 소스 — WS vs REST

- **WS 실시간 체결**: `realtime:{code}` Redis 캐시에서 `current_price` 읽기. 가장 빠르고 정확.
- **WS 미수신 시 REST 폴백**: `get_current_price()` REST API 호출. 지연 ~1초.
- **갱신 주기**: 5초 간격이면 단타에 적절. 1초는 API 부하 과다.
- **주의**: WS 데이터는 `stck_prpr` (현재가) 필드. 장 시작 전에는 0 또는 전일 종가 → 09:00 이전 갱신 시 잘못된 청산 발동 방지 필요.
- **권고**: 장 시간(09:00~15:30) 내에서만 가격 갱신 실행.

### 체결가 기반 포지션 생성

- 모의거래에서 체결가(filled_price)를 정확히 받아야 함.
- 모의거래 체결 응답의 `filled_price`는 실전과 다를 수 있음 (시장가 주문 시 실전: 즉시 체결가, 모의: 신청가 또는 종가 기준).
- **권고**: `_poll_fill_status`에서 `tot_ccld_amt` / `tot_ccld_qty`로 평균 체결가 역산.

### 청산 실행 — 매도 주문 연결

- 현재 `_monitor_positions_loop`에서 청산 대상을 로깅만 함.
- **수정 방향**: 청산 대상에 대해 `OrderManager.submit_sell_order()` 호출 → 체결 후 `close_position()`.
- **주의**: 매도 주문도 체결 폴링이 필요. 체결 실패 시 EOD 청산으로 폴백.
- **권고**: 청산 매도는 시장가("01") 고정. 지정가 불필요 (빠른 청산이 최우선).

### trade_strength_min 조정

- 실전 CTTR 값은 보통 100~200 범위.
- 모의 환경의 CTTR는 실시간 체결 데이터가 제한적이라 낮게 나옴.
- **60이 적절**. 실전 전환 시 65~70 범위로 단계적 상향.

### max_candidates 조정

- 단타 매매에서 30종목 동시 감시는 과다. 집중도 분산.
- 20종목이면 상위 모멘텀에 집중 가능. WS 안정성도 확보.
- **권고**: LIVE 첫 주는 10종목으로 시작, 이후 20까지 확대.

## 3. 파라미터 조정 권고

| 항목 | 원래값 | 권고값 | 근거 |
|------|--------|--------|------|
| trade_strength_min | 70 | 60 (Paper), 65 (LIVE 초기) | 모의/실전 CTTR 차이 |
| max_candidates | 30 | 20 (Paper), 10 (LIVE 첫 주) → 20 (안정 후) | 집중도 + WS 안정성 |
| 포지션 모니터링 간격 | 5초 | 5초 유지 | 적절. 1초는 과다 |
| 청산 매도 주문 방식 | 없음 | 시장가 고정 | 빠른 청산 최우선 |
| 가격 갱신 시간대 | 없음 | 09:00~15:30만 | 장외 시간 잘못된 청산 방지 |

## 5. 리스크 및 대안

- **최대 리스크**: 모의/실전 체결 차이로 인한 슬리피지. 모의에서 잘 되던 전략이 실전에서 손실.
- **대안**: LIVE 첫 주는 semi-auto 모드. 모든 주문에 수동 승인 필요.
- **관찰 포인트**: 체결 소요 시간, 슬리피지 비율, 신호 발생 빈도.
