## 2. 항목별 검증 결과

### 스케줄 의존성 — 매매 엔진 연동
- **핵심 지적**: 후속 스케줄 중지만으로는 부족. 장전 수집이 실패하면 **매매 엔진 자체를 "데이터 불완전" 상태로 전환**해야 함
- 09:00에 market_open이 실행되더라도 1차 스크리닝 결과가 없으면 WS 구독 대상이 없어 실질적 매매 불가이나, 이전 날 스크리닝 결과가 남아있으면 잘못된 종목으로 매매할 위험
- **권고**: `pipeline_healthy` 플래그를 Redis에 저장하고, 매매 엔진이 신호 처리 전 이 플래그를 확인

### ETF sanity check
- **권고**: 단순 ±50%가 아닌 조건부 로직
  - `prev_count == 0` 또는 `prev_count < 200`: sanity check 변동률 검증 스킵 (최초 적재)
  - `prev_count >= 200`: ±30%로 완화 (10%는 너무 엄격, 50%는 너무 관대)
- **근거**: 실제 ETF/ETN 상폐/신규 상장은 연간 수십 건 수준이므로 30%면 충분한 여유

### 파이프라인 실패 알림
- **필수 포함 정보**: 어떤 단계에서 실패했는지, 수동 복구 방법, 다음 자동 시도 시각
- 텔레그램 알림은 실패 즉시 + 수동 복구 성공/실패 시 발송

## 3. 파라미터 조정 권고

| 항목 | 원래 설계 | 권고값 | 근거 |
|------|----------|--------|------|
| ETF sanity check 변동 허용 | ±10% | **±30%** (단, prev < 200이면 스킵) | 상폐/신규 상장 연간 수십 건, seed→mst 전환 대응 |
| 파이프라인 건강 플래그 | 없음 | **Redis `scheduler:pipeline_healthy` 플래그** | 불완전 데이터 기반 매매 차단 |
| 매매 엔진 자동 정지 | 없음 | **pipeline_healthy=false 시 신호 처리 차단** | 최악 시나리오 방어 |

## 4. 리스크

- Redis 장애 시 pipeline_healthy 플래그도 소실 → 기본값을 `false`(보수적)로 설정
- 수동 파이프라인 재실행 성공 시 pipeline_healthy를 `true`로 복원하는 로직 필수
