## 항목별 검증 결과

### 1. 단순화 방향: KIS를 08:00 주 경로로
- **판정**: ✅ 적극 지지
- 포털이 "T+1 영업일 13시 이후" 정책이라면 08:00 포털 호출은 **구조적으로 실패하는 코드**
- "기회주의적 시도"는 운이 좋으면 동작하는 코드 — MVP 원칙에 위배
- KIS 일봉은 이미 전 종목 OHLCV 완비, 내장 3회 재시도 — 충분히 안정적
- **"동작하는 소프트웨어가 완벽한 문서보다 가치 있다"**: 확실히 동작하는 경로를 주 경로로

### 2. Sprint 축소: 2개 -> 1개
- **판정**: ✅ 통과
- 기존 Sprint 1의 복잡한 상태 관리(portal_fresh, streak 카운터)가 제거됨
- 기존 Sprint 2의 백필은 기존 `trigger_premarket_date` API로 수동 실행 가능
- 전체 작업량이 크게 줄어 1개 Sprint로 충분
- **"한 스프린트에 하나의 핵심 목표"**: 08:00 KIS 전환 + 16:00 포털 추가 = 하나의 응집된 목표

### 3. 16:00 포털 보조 수집
- **판정**: ✅ 통과
- 포털 필요 필드가 market_cap + listed_shares 2개뿐
- 장 종료 후 16:00이면 포털 데이터 확실히 존재 (D-1까지 배포됨)
- 기존 `collect_all(target_date=...)` 그대로 사용 가능 — 신규 개발 최소
- 수집 범위: **전 종목** (스크리닝 통과 종목만 하면 다음 날 후보 변동 시 누락 위험)

### 4. 상태 관리 제거
- **판정**: ✅ 강력 지지
- `portal_fresh`, `validate_portal_freshness`, KIS streak 카운터, 알림 승급 로직 — 전부 불필요
- 상태가 없으면 버그도 없다. 디버깅 복잡도 대폭 감소
- 기존 Phase 6.2 초안의 핵심 복잡성이 이 상태 관리에서 비롯됨

### 5. 08:30 retry 전환
- **판정**: ⚠️ KIS 재시도로 전환 권고
- 08:30에 포털을 재시도하는 것은 이제 의미 없음 (08:00에 KIS를 쓰니까)
- 대안 1: 08:30 retry를 **완전 제거** — 가장 단순
- 대안 2: 08:30 retry를 **KIS 실패 시 KIS 재시도**로 전환 — 안전 마진
- **권고**: 대안 2. KIS도 간헐적으로 실패할 수 있음. 08:30에 한 번 더 시도하는 건 저비용 보험
