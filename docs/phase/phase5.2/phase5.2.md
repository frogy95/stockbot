## 개요

프로덕션(Railway, TRADING_ENV=paper)에서 KIS WebSocket이 **지속적으로 재연결을 반복**하며 장중 실시간 파이프라인(2차 스크리닝 + 매매 신호)이 마비되는 문제를 수정한다.

### 문제 분석

```
[2026-04-08 프로덕션 로그 분석]

1. 1차 스크리닝 통과: ~30종목 -> WS 구독 시도
2. WSSubscriptionManager.max=35 -> 30종목 x 2 tr_id = 60 WS 구독
3. 초기 구독: 60건이 순차적으로 등록되어 정상 동작 (한도 내)
4. 모의 서버 불안정으로 10~30분 간격 연결 해제 발생
5. _reconnect() -> 60건을 딜레이 없이 한꺼번에 재구독 -> 서버 과부하로 즉시 재해제
6. 재연결 -> 버스트 재구독 -> 재해제 -> 무한 루프
7. Redis 실시간 캐시 TTL=5초 -> 데이터 만료 -> 2차 스크리닝 무효화
8. 10:14 이후 2차 스크리닝 실질 중단
```

### 근본 원인

1. **재연결 시 버스트 전송 (핵심)**: `_reconnect()`에서 기존 구독 60건(30종목 x 2 tr_id)을 딜레이 없이 한꺼번에 전송. 모의 서버가 초당 수십 건의 구독 요청을 처리하지 못하고 연결을 끊음 (`kis_ws.py` 174~175줄)
2. **재연결-버스트-재해제 악순환**: 재연결 성공 -> 60건 버스트 -> 서버 과부하 해제 -> 다시 재연결 -> 무한 루프
3. **원인 미로깅**: ConnectionClosed에서 close code/reason 미출력하여 원인 파악 지연

> **참고**: 초기 구독 시에는 `WSSubscriptionManager.subscribe()`가 종목 단위로 순차 호출되므로 30종목(60 tr_id)도 정상 등록됨. 문제는 **재연결 시 복원**에서만 발생.

### 해결 아키텍처

```
[Sprint 1: WS 재연결 안정화 + 구독 제한]

1. 재연결 로직 안정화 (핵심 수정)
   ├─ 구독 복원 딜레이: 0.5초/종목 (= 0.25초/tr_id) -- 버스트 전송 방지
   ├─ 백오프 기저: 1초 → 2초, 최대 시도: 5 → 7
   ├─ ping_timeout=10초 추가
   ├─ ConnectionClosed close code/reason 로깅
   └─ 재연결 실패(7회) 시 텔레그램 긴급 알림

2. 환경별 구독 제한 (안전 마진)
   KISEnvironment.max_ws_subscriptions 필드 추가
   ├─ PAPER: 25종목 (25 x 2 = 50 WS 구독)
   └─ LIVE: 35종목 (70 WS 구독, 실전 한도 충분)
   ※ 30종목도 정상 동작하나, 재연결 복원 부하 감소를 위해 25종목으로 안전 마진 확보

3. 2차 스크리닝 WS 연동
   ├─ WS 미연결 시 스킵 + 경고 로그
   └─ 연속 3회 스킵 시 텔레그램 경고

4. 데이터 안정화
   ├─ REALTIME_CACHE_TTL: 5초 → 10초
   └─ 재연결 후 체결강도 5초 웜업 구간

5. 테스트
   ├─ 재연결 딜레이/실패 테스트
   ├─ 환경별 구독 제한 테스트
   └─ 2차 스크리닝 WS 미연결 스킵 테스트
```

## 검토팀 확정 파라미터 (2026-04-08)

> 정프로(PO), 최리스크(리스크관리), 윤에이피(API), 김단타(단타) — 4명 검토 완료

| # | 항목 | 원래 설계 | 확정값 | 근거 |
|---|------|----------|--------|------|
| 1 | paper max_ws_subscriptions | 35 (환경 구분 없음) | **25** | rev.2 수정. 30종목(60 tr_id)이 초기 구독 시 정상 동작 확인. 구독 수 초과가 아닌 재연결 버스트가 원인. 25종목(50 tr_id)으로 재연결 복원 부하 감소 + 1차 스크리닝 상위 커버 |
| 2 | live max_ws_subscriptions | 35 | **35 유지** | 전원 합의. 실전 한도 충분. 실전 테스트 후 조정 가능 |
| 3 | 재연결 구독 복원 딜레이 | 0 (즉시) | **0.5초/종목** | **핵심 수정**. 윤에이피: 0.25초/tr_id = 0.5초/종목. 재연결 시 버스트 전송이 근본 원인이므로 이 파라미터가 가장 중요. 실전은 0.2초/종목 |
| 4 | 재연결 최대 시도 (MAX_RECONNECT_ATTEMPTS) | 5 | **7** | 최리스크: 5회=31초, 7회=254초(~4분). 모의 서버 회복 대기 충분 |
| 5 | 재연결 백오프 기저 (BACKOFF_BASE) | 1초 | **2초** | 최리스크: 모의 서버 부하 회복 시간 감안. 2초 시작이 안전 |
| 6 | ping_timeout | 미설정 (라이브러리 기본) | **10초** | 윤에이피: 모의 서버 ping 응답 지연 대비. websockets.connect(ping_timeout=10) |
| 7 | REALTIME_CACHE_TTL | 5초 | **10초** | 전원 합의. 재연결 중 데이터 유지. 30초 스크리닝 주기 대비 적절 |
| 8 | 재연결 실패 시 텔레그램 알림 | 없음 | **필수** | 최리스크: 7회 실패 시 긴급 알림. 장애 인지 지연 방지 |
| 9 | 2차 스크리닝 WS 미연결 대응 | 실행 시도 (데이터 없어 무의미) | **스킵 + 연속 3회 시 텔레그램 경고** | 정프로+최리스크: 무음 스킵은 장애 인지 지연 |
| 10 | 재연결 후 체결강도 웜업 | 없음 | **5초 무시 구간** | 김단타: 재연결 직후 데이터 갭으로 비정상 체결강도 방지 |
| 11 | 실전 환경 구독 복원 딜레이 | - | **0.2초/종목** | 윤에이피: 실전 서버도 한번에 수십 건 보내면 일부 누락 |
