## 1. 전문가별 의견

### 1.1 김단타 (주식거래 단타 전문가)

#### 검증 결과 평가

체결강도 필드가 N/A로 나온 건 상당히 중요한 문제다. 실전 단타에서 체결강도는 매수/매도 세력의 우위를 판단하는 핵심 지표인데, 현재가 API에서 바로 안 나온다면 직접 계산해야 한다. 매수 체결량 누적 대비 매도 체결량 누적으로 계산하면 되는데, 이건 웹소켓 체결 데이터를 실시간으로 쌓아야 가능하다. REST 폴링으로는 정확도가 떨어진다.

장상태 전용 API가 없다는 것도 문제다. 시초가 30분, 장마감 30분은 변동성이 완전히 다르기 때문에 장 상태를 정확히 알아야 전략을 바꿀 수 있다. `iscd_stat_cls_code` 필드로 간접 확인한다고 했는데, 이게 실시간으로 정확한 장 오픈/클로즈 시점을 잡아주는지 평일에 반드시 검증해야 한다. 안 되면 시간 기반 스케줄(08:30 프리마켓, 09:00 정규장, 15:30 마감)로 가는 게 현실적이다.

네이버 뉴스 지연이 대형주 6분, 중소형 100분 이상이라면 단타에서 뉴스 속보 트리거는 포기하는 게 맞다. 삼성전자급 대형주도 6분이면 이미 호가가 반영된 뒤다. 센티멘트 분석 정도로 활용 범위를 제한하는 게 맞다.

#### ROADMAP 수정 제안

1. **Phase 2**: 체결강도를 웹소켓 체결 데이터 기반으로 직접 계산하는 모듈을 추가해야 한다. 이건 스크리닝의 핵심 팩터이므로 Phase 2 Sprint 1에 포함되어야 한다.
2. **Phase 1**: 장상태 감지를 시간 기반 스케줄 + `iscd_stat_cls_code` 간접 확인 이중 체계로 설계. 시간 기반이 1차, API 확인이 2차 검증.
3. **Phase 2**: 네이버 API를 뉴스 속보 용도에서 완전히 제외. 일 1~2회 배치 수집으로 센티멘트 트렌드만 파악.
4. **Phase 1**: Rate Limit 1.5초 간격이 적정. 다만 장중 서버 부하 시 더 느려질 수 있으므로 동적 스로틀링(에러 발생 시 간격 증가)이 필요하다.

### 1.2 박퀀트 (퀀트투자 기법 전문가)

#### 검증 결과 평가

통계적 관점에서 몇 가지 중요한 시사점이 있다.

첫째, 체결강도를 직접 계산해야 한다면, 이는 오히려 기회가 될 수 있다. 원시 체결 데이터로부터 직접 계산하면, 계산 방법을 커스터마이징할 수 있다. 단순 매수/매도 비율뿐 아니라, 시간 가중 체결강도, 대량 체결 가중치 등 더 유의미한 팩터를 만들 수 있다.

둘째, 공공데이터포털의 일 1,000건 제한은 심각한 문제다. 스크리닝에 시가총액을 팩터로 사용하려면 KOSPI 800 + KOSDAQ 1,600 = 2,400건이 필요한데, 일 한도의 2.4배다. 이 문제를 해결하지 않으면 스크리닝 팩터에서 시가총액을 제외해야 하는데, 시가총액은 유동성 필터로 매우 중요하다.

셋째, DART API에서 에코프로비엠 재무정보 조회 실패는 corp_code 매핑 문제일 수 있지만, 중소형주에서 재무 데이터 불완전할 가능성을 시사한다. 스코어링 알고리즘에서 재무 팩터 누락 시 폴백 로직이 필요하다.

넷째, ETF가 DART/공공데이터포털에서 재무/시총을 제공하지 않으므로, ETF 전용 스코어링 팩터 세트를 별도로 설계해야 한다. NAV, 괴리율, 추적오차 등 ETF 고유 팩터를 한투 API에서 추출할 수 있는지 확인이 필요하다.

#### ROADMAP 수정 제안

1. **Phase 2**: 공공데이터포털 시가총액 데이터 수집 전략을 '일 전수 수집'에서 '캐싱 + 증분 수집'으로 변경. 시가총액은 하루에 한 번 갱신되므로, DB에 캐싱하고 신규 상장/변동분만 업데이트. 또는 한투 API 현재가 응답의 시가총액 관련 필드를 대안으로 활용.
2. **Phase 2**: ETF 전용 스코어링 팩터 모듈 추가. 기존 주식 스코어링과 분리하여 ETF 팩터(NAV, 괴리율, 거래량 대비 순자산)를 별도 설계.
3. **Phase 2**: 재무 데이터 팩터에 '데이터 없음' 폴백 로직 구현. 재무 데이터 미제공 종목은 해당 팩터를 중립(0.5) 처리하거나 가용 팩터로만 스코어링.
4. **Phase 2**: 체결강도 직접 계산 시, 단순 비율 외에 시간 가중 변형도 실험 가능하도록 팩터 인터페이스를 유연하게 설계.

### 1.3 이자산 (펀드매니저)

#### 검증 결과 평가

거시적 관점에서 보면, 이번 검증 결과는 우리 시스템의 정보 소스 다양성에 제약이 있다는 점을 보여준다.

운용사에서는 블룸버그 터미널, 에프앤가이드 같은 유료 데이터 소스를 쓰지만, 개인이라면 이런 무료 API 조합으로 가야 하는 건 현실적인 선택이다. 다만 정보의 질 차이는 인지하고 있어야 한다.

네이버 뉴스 지연과 DART 실시간성 부족은 시장 전체 분위기를 파악하는 데 한계가 있다는 뜻이다. 단타에서 시장 분위기(마켓 센티멘트)는 중요하다. 시장 전체가 빠질 때 개별 종목 매수에 들어가면 큰 손실을 볼 수 있기 때문이다.

ETF 데이터가 DART/공공데이터포털에서 제한적인 것은 ETF 활용 전략을 재고해야 한다는 신호다. 레버리지/인버스 ETF를 시장 방향성 베팅에 쓰려면, ETF 고유 데이터(괴리율, LP 물량, 설정/환매 동향)가 필요한데, 이 데이터를 어디서 가져올지 Phase 2 전에 확인해야 한다.

공공데이터포털 일 1,000건 제한은 포트폴리오 관점에서도 문제다. 전 종목 시가총액을 알아야 시장 전체 상황(대형주/중형주/소형주 로테이션)을 파악할 수 있기 때문이다.

#### ROADMAP 수정 제안

1. **Phase 2**: 시장 센티멘트 지표를 별도 모듈로 분리. KOSPI/KOSDAQ 지수 변동, 외인/기관 순매수 데이터(한투 API에서 조회 가능한지 확인)를 활용하여 시장 방향성을 판단하는 '마켓 필터' 기능을 추가.
2. **Phase 2~3**: ETF 전략의 범위를 재정의. 레버리지/인버스 ETF를 포함할 거라면, ETF 전용 데이터 소스 확보 방안을 Phase 2 계획 시 확정. 한투 API에서 ETF NAV/괴리율 조회 가능 여부를 Phase 1 Sprint 2에서 추가 검증.
3. **Phase 3**: 시장 전체 하락 시 매매를 자동 중단하는 '마켓 회로차단기' 기능을 리스크 관리 모듈에 포함.
4. **전체**: 비용을 과소평가하지 말 것. 단타의 경우 거래 수수료와 슬리피지가 누적되므로, Phase 5 성과 분석에서 수수료/세금 차감 후 순수익률을 반드시 계산.

### 1.4 최리스크 (리스크관리 전문가)

#### 검증 결과 평가

리스크 관점에서 이번 검증 결과에는 즉시 대응이 필요한 사항이 여럿 있다.

**가장 위험한 발견: 잘못된 종목도 HTTP 200 반환.** 이건 심각하다. 존재하지 않는 종목에 대해 에러 없이 빈 데이터를 반환한다면, 잘못된 종목 코드로 주문이 들어가는 시나리오가 가능하다. 주문 전 종목 유효성 검증을 반드시 구현해야 하고, 이건 Phase 1에서 해결해야 할 보안/안전 이슈다.

**두 번째 위험: 모의 주문 미테스트.** 핵심 기능인 주문 실행을 아직 검증하지 못했다. 주문 실행, 체결 확인, 취소, 정정 — 이 전체 주문 라이프사이클을 평일에 반드시 테스트해야 한다. Phase 1 진입 전에 완료되어야 한다.

**세 번째 위험: 웹소켓 30분 유지 미검증.** 웹소켓이 장중에 끊기면 실시간 시세가 중단되고, 이는 포지션 모니터링 불가로 이어진다. 재연결 시 재구독이 필요하다는 점은 확인했으나, 장중 6시간 연속 안정성은 미확인이다.

**네 번째 위험: Rate Limit 동적 변동 가능성.** 실측이 공식보다 관대하다고 해서 공식 한도 이상 사용하면 안 된다. 장중 서버 부하가 높을 때 한도가 더 엄격해질 수 있다. 공식 한도의 70%를 기준으로 설계하되, 에러 발생 시 자동 백오프해야 한다.

#### ROADMAP 수정 제안

1. **Phase 1 (긴급)**: 종목 코드 유효성 검증 레이어 추가. 종목 마스터 테이블에 없는 코드는 주문 불가. 시세 조회 응답의 데이터 값 검증(가격=0, 거래량=0이면 유효하지 않은 종목으로 판단).
2. **Phase 1 (필수)**: 모의 주문 전체 라이프사이클 테스트를 Phase 1 Sprint 2의 완료 기준에 명시. 주문 실행/체결/취소/정정 모두 성공해야 Sprint 완료.
3. **Phase 1**: Rate Limit 스로틀링을 '고정 간격'이 아닌 '적응형 백오프'로 설계. 기본 1.5초 간격, 에러 발생 시 간격 2배 증가, 성공 시 점진적 복구.
4. **Phase 1**: 웹소켓 연결 모니터링 + 자동 재연결 + 재구독 로직을 Phase 1 Sprint 2 필수 항목에 포함.
5. **Phase 3**: 레버리지/인버스 ETF의 리스크 한도를 일반 종목 대비 50% 이하로 설정. 변동성이 2~3배이므로 포지션 크기를 그만큼 줄여야 한다.
6. **전체**: 비상 정지(kill switch) 기능을 Phase 3이 아닌 Phase 1에서 기본 구조라도 구현. 시스템 장애 시 모든 주문을 중단하는 최소한의 안전장치가 있어야 한다.

### 1.5 정프로 (PO / 프로젝트 관리)

#### 검증 결과 평가

프로덕트 관점에서 정리하면, Phase 0.5의 검증은 매우 가치 있는 결과를 냈다. 불확실한 것을 미리 검증한 것이 이후 Phase의 리스크를 크게 줄였다.

핵심 판단:
- **한투 API**: Go. 시세+주문의 핵심 기능이 동작한다. 미테스트 항목(주문, 웹소켓 30분)은 평일에 반드시 추가 검증.
- **텔레그램**: Go. 지연 0.5초면 충분하다.
- **네이버**: Conditional. MVP에서의 역할을 축소한다. 센티멘트 분석은 "Should" 기능이므로, Phase 2에서 기본 연동만 하고 본격 활용은 Phase 6으로 미룬다.
- **DART**: Conditional. 재무 데이터만 활용. 실시간 공시는 MVP 범위에서 제외한다.
- **공공데이터포털**: Go이지만 Rate Limit 이슈가 있다. 수집 전략 조정이 필요하다.

1인 개발 프로젝트의 현실을 감안하면, 범위를 좁히는 것이 맞다. 네이버/DART 연동에 시간을 많이 쓰는 것보다, 한투 API 연동의 완성도를 높이는 게 MVP 가치를 극대화한다.

#### ROADMAP 수정 제안

1. **Phase 2 범위 축소**: 네이버 API 연동을 Phase 2 Sprint 1에서 제외하고 Phase 6으로 이동. DART API도 '기본 재무 조회'만 Phase 2에 남기고, 공시 모니터링은 Phase 6으로 이동.
2. **Phase 2 Sprint 1 재구성**: '데이터 수집 시스템'에 집중 — 한투 API 시세 수집 + 공공데이터포털 시총 수집(캐싱 전략 포함) + DART 재무 기본 조회. 네이버 연동 제외.
3. **Phase 1에 추가**: 미완료 검증 항목(모의 주문, 웹소켓 장중 테스트)을 Phase 1 Sprint 1 또는 별도 "검증 스프린트"로 처리.
4. **Phase 2 Sprint 2**: ETF 예외 처리를 스크리닝 엔진에 포함. ETF 전용 팩터 세트를 Phase 계획 시 확정.
5. **전체 일정**: Phase 2의 범위가 줄었으므로 Sprint 수를 2 -> 1.5(Sprint 2를 작게)로 조정 가능. 단, 여유분은 Phase 1 미완료 검증에 할당.

### 1.6 윤에이피 (API 연동 전문개발자)

#### 검증 결과 평가

API 연동 관점에서 구체적으로 짚어야 할 사항이 많다.

**한투 API — 에러 핸들링이 까다롭다.** 잘못된 종목이 HTTP 200을 반환하는 건 한투 API의 고질적 문제다. 문서에는 `rt_cd`로 성공/실패를 판단하라고 되어있지만, 실제로는 `rt_cd=0`(성공)이면서 데이터가 빈 경우가 있다. 반드시 응답 데이터 자체를 검증해야 한다. `stck_prpr`(현재가)가 "0"이면 유효하지 않은 종목으로 판단하는 방어 로직이 필요하다.

**Rate Limit — 1.5초 권장에 동의하지만 추가 설계가 필요하다.** 토큰 발급은 1분당 1회 제한이 명확하므로 토큰을 Redis에 캐싱하고, 만료 1시간 전에 갱신하는 전략이 필요하다. 시세 조회의 경우, 장중 09:00~15:30에는 서버 부하가 높아서 실측보다 더 엄격해질 수 있다. 모의거래 환경에서의 실측이므로 실전 환경은 다를 수 있다는 점도 유의.

**웹소켓 — 재구독이 핵심이다.** 재연결은 0.016초로 빠르지만, 재연결 후 모든 종목을 재구독해야 한다. 구독 중인 종목 목록을 메모리에 항상 유지하고, 재연결 이벤트 시 자동 재구독하는 로직이 필수다. 또한 heartbeat/ping 메커니즘이 있는지 확인해야 한다. 30분 유지 미검증은 장중에 반드시 확인.

**공공데이터포털 일 1,000건 — 해결책이 있다.** 시가총액 데이터는 하루 1회 갱신이므로, 매일 장 시작 전(08:00) 한 번만 전체 수집하면 된다. 1,000건이 1회 호출 한도인지 일일 총 한도인지에 따라 전략이 달라진다. 1회 호출에 100건씩 페이징한다면 24페이지(2,400건)가 필요하고, 이게 일일 24건 호출이므로 한도 내다. 만약 일일 총 응답 건수 한도라면, KOSPI 800건(상위 종목 위주)만 수집하고 KOSDAQ은 한투 API 현재가 응답에서 시가총액 관련 필드를 추출하는 방안을 검토.

**네이버 API — 종목명 검색이 종목코드보다 관련성이 높다는 건 중요한 발견이다.** 검색 키워드 전략을 종목명 기반으로 설계해야 한다. 또한 동음이의어 문제(예: "현대" 검색 시 현대차/현대건설/현대중공업 혼재)를 처리하는 필터링 로직이 필요하다.

**DART API — corp_code 매핑 테이블을 사전에 구축해야 한다.** DART는 종목코드가 아닌 고유 corp_code를 사용하므로, 종목코드 -> corp_code 매핑 테이블을 Phase 2 시작 시 일괄 다운로드하여 DB에 저장해야 한다. 에코프로비엠 조회 실패도 이 매핑 문제일 가능성이 높다.

#### ROADMAP 수정 제안

1. **Phase 1 Sprint 2**: 한투 API 클라이언트에 방어적 응답 검증 레이어 추가. `rt_cd` + 데이터 값 이중 검증. 에러 응답을 구조화된 예외로 변환하는 미들웨어 설계.
2. **Phase 1 Sprint 2**: Rate Limit 스로틀링을 적응형 백오프로 구현. 기본 간격 1.5초, 에러 시 지수 백오프(1.5 -> 3 -> 6초), 성공 시 점진 복구(6 -> 3 -> 1.5초).
3. **Phase 1 Sprint 2**: 웹소켓 구독 관리자(subscription manager) 설계. 구독 목록 유지, 재연결 시 자동 재구독, heartbeat 모니터링.
4. **Phase 2 Sprint 1**: 공공데이터포털 수집을 '페이징 기반 일일 배치'로 설계. 1회 호출당 100건 x 24페이지 = 2,400건. 일일 한도 확인 후 전략 확정.
5. **Phase 2 Sprint 1**: DART corp_code 매핑 테이블을 일괄 다운로드하여 종목 마스터 테이블과 연동. 매핑 누락 종목은 재무 팩터 제외 처리.
6. **Phase 2**: 텔레그램 메시지 형식을 HTML로 통일. MarkdownV2의 이스케이프 복잡성 회피.

### 1.7 한유엑 (UX 전문가)

#### 검증 결과 평가

사용자 경험 관점에서 검증 결과가 시사하는 바가 있다.

텔레그램 지연 0.49초 평균은 좋은 결과다. 사용자가 매매 승인 요청을 받고 의사결정하는 데 이 정도 지연은 체감되지 않을 것이다. 다만 최대 1.03초인 점을 고려하면, 승인 메시지에 "요청 시각"을 명시하여 사용자가 정보의 시점을 인지할 수 있게 해야 한다.

MarkdownV2보다 HTML을 권장한다는 결과는 UX에도 영향을 준다. HTML이면 텔레그램 메시지에서 더 풍부한 포맷팅(테이블, 색상 강조)을 사용할 수 있다. 매매 신호 알림에서 핵심 숫자(현재가, 목표가, 손절가)를 볼드 처리하고, 손익 방향을 시각적으로 구분할 수 있다.

장상태 전용 API가 없다는 점은 대시보드 UX에 영향을 준다. 사용자가 대시보드를 열었을 때 "현재 장이 열려있는지, 닫혀있는지"를 즉시 알 수 있어야 한다. 장 마감 후에는 실시간 데이터가 업데이트되지 않으므로, "장 마감 — 마지막 업데이트: 15:30" 같은 상태 표시가 필요하다.

ETF 데이터 제한(DART/공공데이터포털)은 대시보드에서 ETF 종목의 정보 표시가 주식과 다를 수 있다는 뜻이다. 사용자에게 "이 종목은 ETF이므로 재무 데이터가 제공되지 않습니다" 같은 안내를 자연스럽게 보여줘야 한다. 빈 칸으로 두면 오류처럼 보인다.

#### ROADMAP 수정 제안

1. **Phase 3 Sprint 3**: 텔레그램 메시지 형식을 HTML 기반으로 설계. 매매 신호 알림 템플릿에 요청 시각, 핵심 숫자 볼드, 손익 방향 이모지(상승/하락) 포함.
2. **Phase 4 Sprint 1**: 대시보드에 '장 상태 인디케이터' 추가. 프리마켓/정규장/장마감/휴장을 시각적으로 구분. 장 마감 후에는 "마지막 업데이트 시각" 표시.
3. **Phase 4**: ETF 종목의 정보 표시 UX를 별도 설계. 재무 데이터 미제공 항목은 "N/A" 대신 "ETF 종목"이라는 맥락 설명 표시.
4. **Phase 4**: 실전/모의 모드 구분 시, 모의 모드에서의 시세 데이터가 실전과 다를 수 있다는 점(모의 체결 로직 차이)을 사용자에게 명확히 고지.
5. **Phase 3**: 승인 타임아웃 카운트다운을 텔레그램 메시지에 표시 (예: "60초 내 미응답 시 자동 만료"). 승인 버튼은 크고 명확하게.

## 2. 합의된 수정 사항

7명 전문가가 공통적으로 동의하는 수정 항목:

### 2.1 [긴급] 종목 코드 유효성 검증 (Phase 1)

> **합의**: HTTP 200이면서 빈 데이터를 반환하는 한투 API 특성상, 종목 코드 유효성 검증은 시세 조회/주문 실행의 전제 조건이다.

- 종목 마스터 테이블 기반 사전 검증
- 시세 응답 데이터 값 검증 (현재가=0이면 무효)
- 주문 전 이중 검증 필수

### 2.2 [필수] Rate Limit 적응형 백오프 (Phase 1)

> **합의**: 고정 간격(초당 1건)이 아닌 적응형 백오프로 설계. 기본 1.5초, 에러 시 지수 증가, 성공 시 점진 복구.

- 공식 한도의 70% 기준(윤에이피 원칙)
- 장중 서버 부하 시 더 보수적으로 동작

### 2.3 [필수] 체결강도 직접 계산 (Phase 2)

> **합의**: 현재가 API에서 체결강도 미제공이므로, 웹소켓 체결 데이터 기반 직접 계산 모듈을 Phase 2에 추가.

- 매수 체결량 누적 / 매도 체결량 누적 기본 계산
- 스크리닝 핵심 팩터로 활용

### 2.4 [필수] 네이버/DART 범위 축소 (Phase 2)

> **합의**: 두 API 모두 Conditional이므로 Phase 2에서의 활용 범위를 최소화.

- 네이버: Phase 2에서 제외, Phase 6에서 센티멘트 분석 용도로 도입
- DART: 기본 재무 조회만 Phase 2에 남기고, 공시 모니터링은 Phase 6으로 이동

### 2.5 [필수] 공공데이터포털 수집 전략 변경 (Phase 2)

> **합의**: 일 1,000건 한도 대응을 위해 '매일 전수 수집'에서 '캐싱 + 페이징 배치'로 전략 변경.

- 페이징 호출(1회 100건 x 24페이지)로 일일 한도 내 수집 가능 여부 확인
- 불가 시, 한투 API 현재가 응답의 시총 관련 필드로 대안 확보

### 2.6 [필수] ETF 예외 처리 체계 (Phase 2~4)

> **합의**: ETF는 DART 재무/공공데이터포털 시총 미제공이므로 별도 처리 필요.

- Phase 2: ETF 전용 스코어링 팩터 설계
- Phase 4: 대시보드 ETF 정보 표시 UX 별도 설계

### 2.7 [필수] 장상태 감지 이중 체계 (Phase 1)

> **합의**: 전용 API 없으므로 시간 기반 스케줄(1차) + API 간접 확인(2차)으로 이중 체계 설계.

- 시간 기반: 08:30 프리마켓, 09:00 정규장, 15:30 마감, 공휴일 캘린더
- API 간접: `iscd_stat_cls_code` 필드 활용 (평일 검증 후 확정)

### 2.8 [필수] 미완료 검증 항목 완료 (Phase 1 진입 전)

> **합의**: 모의 주문 라이프사이클, 웹소켓 장중 30분 유지 테스트는 Phase 1 시작 전 또는 Sprint 1에서 완료.

## 3. 논쟁 사항

### 3.1 Rate Limit 기준값: 1.5초 vs 공식 1초

| 전문가 | 의견 |
|--------|------|
| 김단타 | 1.5초면 시세 갱신이 느려질 수 있다. 장중 급변 시 0.5초 차이가 크다. |
| 윤에이피 | 1.5초가 안전하다. 공식 한도 초과 시 계정 제재 가능성이 있다. |
| 최리스크 | 안전 마진은 클수록 좋다. 공식 1초의 70%인 1.4초도 고려. |
| 정프로 | 실측이 관대하다고 해도 공식 한도 기준으로 설계하는 게 맞다. |

**절충안**: 기본 간격 1.5초로 설계하되, 시세 조회와 주문의 우선순위를 분리. 주문은 즉시 실행(Rate Limit 소진 우선), 시세 조회는 1.5초 간격 유지. 적응형 백오프로 동적 조절.

### 3.2 공공데이터포털 대안: 한투 API 시총 필드 활용 여부

| 전문가 | 의견 |
|--------|------|
| 박퀀트 | 한투 API 현재가 응답에 시가총액 관련 필드가 있다면 그걸 쓰는 게 API 호출을 줄인다. |
| 윤에이피 | 한투 현재가 응답에 `stck_hgpr`, `stck_lwpr` 등은 있지만 시가총액 직접 필드는 확인 필요. 있더라도 장중 실시간 값이라 전일 기준과 다를 수 있다. |
| 이자산 | 시가총액은 전일 종가 기준이 표준이다. 장중 시총은 변동이 크므로 스크리닝 팩터로 부적합. |

**절충안**: 공공데이터포털의 페이징 호출(일일 한도 내 수집 가능 여부)을 Phase 2 Sprint 1 초기에 먼저 검증. 불가 시 한투 API 시총 필드를 대안으로 검토하되, 전일 종가 기준으로 보정.

### 3.3 네이버 API 도입 시점: Phase 2 vs Phase 6

| 전문가 | 의견 |
|--------|------|
| 정프로 | Phase 6으로 미룬다. MVP에 불필요한 복잡성을 추가하지 않는다. |
| 박퀀트 | 센티멘트 팩터가 스코어링에 유의미한 기여를 할 수 있으므로, Phase 2에서 기본 연동이라도 해두고 싶다. |
| 김단타 | 뉴스 속보는 쓸 수 없지만, 장 시작 전 당일 뉴스 센티멘트 수집은 사전 정보수집에 유용하다. |
| 이자산 | 시장 센티멘트는 중요하지만, 네이버 API 품질이 Conditional인 상태에서 의존하면 오히려 노이즈가 된다. |

**절충안**: Phase 2에서 네이버 API '기본 연동 모듈'만 구현(하루 1~2회 배치 수집). 스코어링에는 반영하지 않고 대시보드에 참고 정보로만 표시. 본격 센티멘트 분석은 Phase 6.

### 3.4 비상 정지(Kill Switch) 도입 시점: Phase 1 vs Phase 3

| 전문가 | 의견 |
|--------|------|
| 최리스크 | Phase 1에서 기본 구조라도 구현. 시스템 장애 시 주문 중단은 최소 안전장치다. |
| 정프로 | Phase 1은 인프라+API 기반이므로 비상 정지 로직은 Phase 3(리스크 관리 모듈)에서 구현하는 게 논리적이다. |
| 윤에이피 | Phase 1에서 주문 실행 자체가 없으므로 kill switch도 필요 없다. Phase 3 Sprint 1(리스크 관리)에서 구현하면 충분. |

**절충안**: Phase 1에서는 설정 플래그(`TRADING_ENABLED=true/false`)로 간단한 on/off만 구현. 본격적인 비상 정지 로직(조건 기반 자동 중단)은 Phase 3 Sprint 1에서 구현.

### 3.5 ETF 전용 스코어링 범위

| 전문가 | 의견 |
|--------|------|
| 김단타 | 레버리지/인버스 ETF는 단타의 핵심 도구. 반드시 Phase 2에서 지원. |
| 최리스크 | 레버리지/인버스 ETF는 리스크가 2~3배. Phase 2에서 지원하더라도 별도 리스크 한도 없이는 위험. |
| 박퀀트 | ETF 스코어링은 주식과 완전히 다른 팩터(NAV, 괴리율, 추적오차)가 필요. Phase 2에서 별도 팩터 세트 설계 가능. |
| 정프로 | ETF 지원은 MVP에 포함하되, 레버리지/인버스는 Phase 5 이후로 미룬다. 일반 ETF(KODEX 200 등)만 Phase 2에서 지원. |

**절충안**: Phase 2에서는 일반 ETF(지수 추종)를 대상으로 기본 스코어링을 구현. 레버리지/인버스 ETF는 Phase 3(리스크 관리) 이후에 별도 리스크 한도와 함께 지원. Phase 계획 시 전문가 확정.

## 5. 결론

Phase 0.5의 API 검증은 프로젝트의 기술적 불확실성을 효과적으로 해소했다. 7명 전문가의 리뷰 결과, 기존 ROADMAP의 핵심 구조(Phase 순서, 의존성)는 유효하나, 각 Phase의 세부 범위와 구현 전략에서 상당한 조정이 필요하다.

가장 큰 변화:
1. **Phase 2 범위 축소**: 네이버/DART 연동을 최소화하고 한투 API 중심으로 집중
2. **체결강도 직접 계산**: 별도 모듈 필요 (Phase 2)
3. **ETF 예외 처리 체계**: 전 Phase에 걸쳐 ETF 전용 로직 필요
4. **방어적 설계 강화**: 종목 유효성 검증, 적응형 Rate Limit, 장상태 이중 체계

이 수정 사항들은 Phase 1 계획(phase-planner) 시 반영되어야 하며, Phase 2 이후의 상세 계획도 이 리뷰 결과를 기반으로 수립되어야 한다.
