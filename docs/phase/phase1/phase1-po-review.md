## 2. 항목별 검증 결과

### Sprint 분할

- 2개 Sprint는 적절하다. Sprint 1은 인프라/기반, Sprint 2는 핵심 외부 연동으로 **관심사 분리가 명확**하다.
- Sprint 1이 완료되어야 Sprint 2를 시작할 수 있는 의존성도 올바르다.

### Sprint 1 범위

- Docker Compose 4컨테이너 + FastAPI 스켈레톤 + DB 스키마 + Redis는 **한 스프린트에 적절한 범위**다.
- 단, DB 스키마는 Phase 1에서 필요한 **최소 테이블만** 생성해야 한다. 전체 스키마를 한 번에 만들면 Phase 2~3에서 변경이 많아진다.
- **권고**: `settings`, `stocks` 테이블 + Alembic 마이그레이션 기반만 Sprint 1에서. `orders`, `positions`, `trade_signals` 등은 Phase 3에서.

### Sprint 2 범위

- 한투 API REST + WebSocket + 토큰 관리 + 모의/실전 전환 + Rate Limit + 장상태 감지 + 시장 어댑터 패턴 — **범위가 넓다**.
- **권고**: 장상태 감지 이중 체계와 시장 어댑터 패턴(base.py + korea.py)은 Phase 1에서 **인터페이스만 정의**하고, 상세 구현은 Phase 2에서 데이터 수집과 함께 완성.
- 웹소켓은 연결/구독/재연결 기본 동작만 확인. 30분 안정성 테스트는 Phase 2 장중 테스트에서.

### 전문가 확정 항목 6건

- 6건 모두 Phase 1 계획 시점에서 확정하는 것이 맞다. Phase 2~3 설계의 전제 조건이므로.
- 단, **Phase 1 코드에 직접 반영되는 항목**은 #1(데이트레이딩 vs 스윙)과 #2(운영 시간대) 정도다.
- 나머지(#3~#6)는 **settings 테이블 스키마와 설정 구조에만 영향**. 구체적 값은 Phase 3 리스크 모듈에서 적용.

## 4. 리스크 및 대안

- **리스크 1**: Sprint 2가 과부하되면 일정 지연. 한투 API 연동은 예상보다 엣지 케이스가 많다.
  - **대안**: Sprint 2를 2a(REST + 토큰) / 2b(WebSocket + Rate Limit)로 분할 가능. 단, 현재는 2개 Sprint 유지하고 범위 축소로 대응.
- **리스크 2**: DB 스키마를 Phase 1에서 너무 많이 정의하면 Phase 2~3에서 마이그레이션 변경이 빈번해진다.
  - **대안**: Alembic 마이그레이션 구조만 잡고, 테이블은 최소한으로.
- **리스크 3**: Next.js 프로젝트를 Sprint 1에서 셋업하면 Phase 4까지 사용하지 않아 의존성 노후화 가능.
  - **권고**: Docker Compose에 Next.js 컨테이너는 포함하되, **빈 프로젝트 + 헬스체크만**. 실제 개발은 Phase 4에서.
