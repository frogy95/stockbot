## 2. 항목별 검증 결과

### 2.1 핫픽스 vs Phase 판단

이 버그는 단순한 파라미터 수정이 아니다. 1차/2차 스크리닝의 팩터 구성 자체를 분리해야 하므로:
- scorer.py의 팩터 리스트/가중치 구조 변경
- screener.py의 후보 빌드 로직 변경
- 기존 테스트 전면 수정
- 임계값 재검토

**판정**: Phase 4.7로 분리. 단일 Sprint로 충분하지만 전문가 검토가 필요한 파라미터 결정이 있으므로 Phase 프로세스를 따른다.

### 2.2 A안 vs B안 평가

**A안 (1차: 3팩터만 사용)**이 MVP 원칙에 부합:
- 1차 스크리닝의 목적은 "실시간 모니터링 대상 종목 선정"
- 실시간 데이터(체결강도, 호가잔량)는 2차 스크리닝에서 사용하는 것이 자연스러움
- 역할 분리가 명확해져 디버깅/운영 용이

**B안의 문제점**:
- percentile=50이 "중립"이라는 가정은 통계적으로 불명확
- 실제로는 정보가 없는 것이므로 "모른다"를 "중간이다"로 바꾸는 것

### 2.3 범위 조정

MVP에서는:
- 1차 스크리닝 3팩터 분리 + 가중치 조정 + 임계값 재검토
- 2차 스크리닝은 기존 5팩터 유지 (실시간 데이터 가용)
- 기존 테스트 업데이트
- 프로덕션 배포 후 다음 거래일 검증

## 3. 파라미터 조정 권고

| 항목 | 원래값 | 권고값 | 근거 |
|------|--------|--------|------|
| 1차 팩터 수 | 5개 (동일 가중) | 3개 (volume, volatility, momentum) | 실시간 데이터 없는 팩터 제외 |
| 1차 가중치 | 각 0.2 | 각 1/3 (~0.333) | 3팩터 균등 배분 |
| 1차 임계값 | 80.0 | 퀀트+단타 전문가 확정 필요 | 3팩터 최대 100점 구조에서 80은 적절할 수 있으나 검증 필요 |
| 2차 팩터 | 기존 5개 유지 | 유지 | 실시간 데이터 가용 시점 |

---

## 4. 리스크 및 대안

- **리스크**: 1차 임계값을 너무 낮추면 2차 스크리닝 부하 증가 (WS 구독 종목 수 증가)
- **대안**: 임계값 대신 상위 N종목(top-K) 방식도 검토 가능 — max_candidates=30이 이미 상한 역할
- **권고**: 1차에서는 is_passed 임계값을 낮추고, max_candidates로 상한을 제어하는 이중 구조가 안전
