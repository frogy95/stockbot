## 2. 항목별 검증 결과

### 2.1 근본 원인 재정의 — ✅ 통과 (rev.2 유지)

기존: "모의투자 서버 ETF 시세 미지원" -> optional 처리
수정: "도메인 라우팅 설계 결함" -> 조회/매매 환경 분리

MVP 관점에서 올바른 방향. optional 처리는 "문제를 덮는 것"이고, 도메인 분리는 "문제를 해결하는 것"이다.

### 2.2 수집 유효성 검증 로직 (rev.3 신규)

**판단: MVP에 넣자 -- Sprint 1 필수**

현재 "0건 수집 = success"는 시스템의 근본 신뢰성 문제다. 이것 없이 나머지 수리는 의미가 없다. 유효성 검증은 단순히 건수 체크가 아니라 **데이터 품질 검증**이어야 한다.

Sprint 1에 통합하되, **검증 로직 자체가 너무 복잡해지지 않도록** 단계적으로:
1. Sprint 1: 최소 건수 + null 비율 + 날짜 검증 + 실패 유형 분류 (필수)
2. Sprint 2: DB 후검증 쿼리 + 신선도 검증 + 휴장일 캘린더 (품질 강화)

### 2.3 ETN 시세 수집 공백 (rev.3 신규)

**판단: Phase 4.6 범위 밖으로 빼자**

- ETN은 현재 매매 대상이 아님 (Phase 3 매매 엔진은 ETF 중심)
- 수집 경로 설계가 필요 (공공데이터포털 미지원, KIS REST 가능 여부 미확인)
- Phase 4.6의 핵심 목표는 "기존 파이프라인 수리"이지 "신규 수집 추가"가 아님
- 미해결 사항에 기록하고 Phase 5에서 검토

### 2.4 Sprint 재구성 (rev.3 신규)

**판단: 2 Sprint 유지하되 Sprint 1 범위 확장**

Sprint 3으로 늘리는 것은 반대한다. 유효성 검증은 에러 전파 수정의 자연스러운 확장이므로 Sprint 1에 통합 가능:
- 에러 전파 수정 = "0건도 success" 방지
- 유효성 검증 = "0건이 아니라도 진짜 유효한지" 확인
- 동일한 코드 영역 (scheduler.py, 각 수집기)에서 작업

### 2.5 수집 범위 이원화 (rev.3 신규)

문서에 현황 기록 필수:
- 일반주식: T+1 일별 시세만 (당일 없음)
- ETF: 당일 시세 (KIS REST)
- ETN: 시세 수집 코드 없음

이 비대칭은 Phase 5에서 검토. 당장은 매매 대상(ETF)의 시세만 확보하면 된다.

## 4. 리스크 및 대안

- **Sprint 1 범위 과대**: 유효성 검증 추가로 Sprint 1이 커지지만, 모두 같은 코드 영역이라 관리 가능
- **유효성 검증 임계값 오탐**: 보수적으로 시작하고 운영 데이터 보면서 조정
- **ETN 방치**: 마스터는 있으므로 stocks 테이블에 존재. 시세만 없는 상태로 운영해도 안정성 영향 없음
- **LIVE 앱키 필수 (기존)**: .env.example 업데이트 필수
- **일정**: Sprint 1 범위 확장이지만, validator 클래스 분리로 코드 정리도 동시 수행
