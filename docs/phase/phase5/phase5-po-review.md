## 2. 항목별 검증

### A. volume_ratio 완화
- **판단**: 88% 탈락 → 0건 통과는 시스템 장애와 동급. 즉시 수정 필요.
- **1.5 적정성**: 최초 배포 후 데이터 축적이 부족한 상황에서 보수적 시작은 맞지만, 2.0은 너무 공격적이었음.

### B. 적응형 필터
- **판단**: "동작하는 소프트웨어" 원칙. 0건보다는 느슨한 필터의 후보가 낫다.
- **주의**: 적응형 결과에 반드시 '완화됨' 마킹 필요 — 텔레그램 알림/대시보드에서 구분.

### C. prev_volume=0 폴백
- **판단**: 319건 탈락은 데이터 초기화 시점의 구조적 문제. 5일 평균 대체는 합리적.

### D. 0건 시 기본 후보
- **판단**: SPOF 해소 목적으로 필요하지만, 대형주 기본 후보의 단타 효율이 낮을 수 있음.
- **권고**: 기본 후보는 '폴백 후보' 명시, 완전 자동 모드에서는 기본 후보로 자동 주문 금지.

### E. date.today() 정리
- **판단**: 기술 부채 정리. 리스크 매니저 파일의 날짜 불일치는 손실 한도 계산 오류 가능성 있어 우선순위 높음.

### F. Sprint 분할
- **우려**: Sprint 1에 A~E를 모두 넣으면 범위가 넓다.
- **권고**: Sprint 1은 A+C+E(즉시 효과, 낮은 복잡도), Sprint 2에 B+D(적응형/폴백, 높은 복잡도) 분리 검토.
- **하지만**: 1인 개발이고 A~E 모두 screening 모듈에 집중. 하나의 Sprint로 묶는 것이 코드 리뷰/테스트 효율적일 수 있음.
- **최종 판단**: Sprint 1에 A~E 유지하되, Task를 명확히 분리하여 순차 구현.
